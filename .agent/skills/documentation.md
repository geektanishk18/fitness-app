# Documentation

**Purpose:** Keep project context durable and concise.

**Use when:** Adding features, changing architecture, schemas, APIs, setup, or known limitations.

**Principles:** Document why, contracts, boundaries, assumptions, and verification—not obvious syntax.

**Workflow:** Identify affected docs before coding, update them with the change, and cross-link only where useful.

**Verification:** Check docs against implementation and commands; remove stale claims and record actual limitations.

**Avoid:** Duplicating the master prompt, speculative promises, and documentation that contradicts the code.
